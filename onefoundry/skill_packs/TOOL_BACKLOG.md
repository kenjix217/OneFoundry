# Skill tool decisions

The [source inventory](source_inventory.json) contains 53 Paperclip and 182 Codex `SKILL.md` files. [One hundred sixty-nine OneFoundry procedures](adapted/manifest.json) adapt concepts from 168 of them and all 12 Paperclip workflow sources. The requested 38 Paperclip, 50 Codex visual/document/template, and 35 Codex engineering/security sources all have procedures; 67 other `SKILL.md` files remain inventory-only. OneFoundry wrote its own bounded procedures from reviewed concepts; it did not import a Paperclip or Codex runtime library. The OneFoundry sidebar's **Tools & Plugins** page shows current connections, but it does not yet show this skill-to-tool decision list. See [requested pack coverage](REMAINING_PACKS.md) and [finance and data pack coverage](FINANCE_DATA_PACKS.md) for source decisions.

**Current boundary:** the Tool Gateway admits run-bound context, local repository, saved coding artifact, approved GitHub PR, and bounded Researcher public-web reads. OpenAI API-key live text profiles use the installed Agents SDK for bounded continuation of admitted tools; public web is restricted to the built-in Researcher. Raw repository and artifact text stay off that provider route until exact content is declassified; the PR tool also needs operator approval wait/resume. Other provider transports remain tool-free. SDK and PostgreSQL tests are local proof, not a live account connection. External coding backends still require proved isolation, authentication, and spending control. A procedure never grants a tool or permission.

## Capabilities to decide

| Order | Capability | OneFoundry owner and decision | What it unlocks |
| --- | --- | --- | --- |
| 1 | Role tool admission | **Internal read-only slice implemented.** Tool Gateway validates the active project/run/profile, snapshot and current allowlists, input, time and output bounds, then records intent and outcome. Tool IDs are immutable contracts: changed semantics need a new ID because run snapshots pin IDs, not versions. Write/connector admission remains separate work. | `current_work_order` is available to admitted trusted callers and the OpenAI API-key SDK route; live account acceptance is still open. |
| 2 | Project context reads | **Internal read-only family implemented.** `project_brief_v1`, `recent_project_work_v1`, `run_evidence_v1`, and `approved_memory_v1` add bounded project-scoped status, one run's result and evidence metadata, and published memory limited by saved and current profile scope. Artifact paths/content and event payloads are excluded. | Admitted trusted callers and OpenAI API-key SDK role runs can inspect current owner records for status, triage, planning, and QA. |
| 3 | Web search and page fetch | **Trusted Researcher tool contracts implemented.** `public_web_search_v1` uses an explicitly configured SearXNG JSON endpoint; `public_page_fetch_v1` fetches bounded text from public HTTPS pages. Both require `PUBLIC_WEB_ENABLED`, saved and current profile allowlists, and source/destination checks. Intent commits before egress; permissions are rechecked before result delivery. | A trusted run-bound caller or admitted OpenAI API-key Researcher can obtain source URLs, dates, snippets, or page text for current-source research; live account acceptance is still open. |
| 4 | Repository and coding evidence | **Bounded role reads implemented, with live gates open.** `coding_evidence_v1` exposes corroborated receipt metadata; `repository_file_v1` reads an exact saved local Git file; `coding_artifact_text_v1` reads a verified saved diff/log; trusted callers can invoke `github_pr_read_v1` after a one-use operator approval. OpenAI API-key role runs have SDK continuation for metadata and web tools with local tests. Exact raw-content declassification, live PR approval wait/resume, provider acceptance, and the external coding runner's isolation/authentication/spending proof remain open. | Authorized roles can inspect supported saved evidence through admitted paths. An installed CLI or text-model account is not proof of a live coding connection. |
| 5 | Browser inspection | **Approval-bound static fixture and operator dispatch implemented.** Private HTML/CSS is bound to one project/run, exact loopback URL, hash, limits, and inbox approval. `browser_static_inspect_v1` is admitted for built-in Researcher and QA profiles with saved/current permission; the operator can dispatch an approved fixture to the run's assigned profile. A separate host bridge claims one job and returns bounded text evidence or an unknown result without retry. The feature is default-off, with exact image IDs and a private host state directory. The live model SDK does not advertise this tool; there is no screenshot store or live-site browser navigation. | Researcher and QA can be assigned approved static inspection on active supported runs. Autonomous role initiation, approval wait/resume, and general visual QA remain open. |
| 6 | Artifact and data workspace | **Bounded text slice implemented.** `decimal_calculate_v1` does exact decimal arithmetic. `write_text_artifact_v1` saves private text, Markdown, or CSV with a committed intent, hash-only events, and operator readback that verifies saved bytes. Other file types, rendering, supplied-data import, and general file access remain open. | Role-authored text artifacts and small calculations under saved/current tool permission; no PDF, slides, charts, images, or spreadsheet runtime yet. |
| 7 | Internal workflow actions | **Draft, QA request, and operator conversion implemented.** `create_draft_work_order_v1` saves a same-project draft. `request_qa_review_v1` records a request targeting the built-in QA profile. The operator can turn one saved request into one linked QA draft with their own title and instructions. The role tools require saved/current run permission; conversion is an operator action with owner readback. None marks ready, starts a run, hands off, approves QA, or schedules recurring work. | Roles can prepare reviewable work and request QA; the operator can create the linked draft and controls later state changes. |
| 8 | Outbound and connected apps | **One GitHub PR comment action implemented.** `github_pr_comment_v1` can propose exact text for a saved source and active role run. The operator can also prepare it in Approvals. A separate approval and explicit one-shot dispatch post a whole-PR issue comment, with readback and no automatic retry. This has fake-transport tests; a live GitHub account and approval wait/resume for SDK role runs remain unverified. Email, publishing, Drive/Notion, finance, cloud, and plugin/MCP actions remain unselected. | The selected workflow can prepare and review a GitHub PR comment under saved/current permission. No other connector is installed by this order. |

## Where the 67 other inventory-only `SKILL.md` files sit

The [full inventory](source_inventory.json) gives every source ID, source type, byte count, and adaptation status. [Requested pack coverage](REMAINING_PACKS.md) identifies the selected Paperclip and Codex source groups and the tool contracts still needed for their full workflows. Some Codex caches repeat the same procedure concept, and 20 entries are pointers to retained template artifacts. A procedure may need several capabilities from the table above. All 12 Paperclip workflow sources inform operator-started procedures, but no recurring scheduler or autonomous wake was installed. Codex-host development procedures do not equip OneFoundry's runner or role agents with those capabilities.

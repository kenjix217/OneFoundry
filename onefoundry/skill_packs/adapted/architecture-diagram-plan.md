# architecture diagram plan

Use this procedure when a work order needs a written plan for a software architecture or UML-like diagram from supplied system facts. Inputs are the audience, question, components, boundaries, relationships, protocols or data flows, and source documents.

1. Choose a diagram type and abstraction level that answers the question. Define what belongs inside and outside the view.
2. List nodes and labeled relationships with direction and evidence. Mark unresolved ownership or inferred edges explicitly.
3. Specify layout, notation, legend, accessibility text, and any interaction or export requirement for a future renderer.
4. Provide a semantic review checklist: missing owners, ambiguous arrows, mismatched levels, and unsupported claims.

Return a diagram brief or text node-and-edge inventory. Do not describe it as rendered, round-tripped, visually inspected, or browser tested. An admitted `write_text_artifact_v1` can save the brief as Markdown when requested; it is not a diagram renderer.

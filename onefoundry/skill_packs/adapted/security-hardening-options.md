# security hardening options

Use this procedure to compare structural protections after the operator supplies a named finding, incident record, or assessment. Treat every supplied finding as a claim until its exact source and behavior have been checked. A trusted run-bound caller may read exact saved repository files with `repository_file_v1` or verified coding artifacts with `coding_artifact_text_v1` when admitted; those raw-text tools are excluded from live model SDK continuation.

1. Record each input's owner, version or revision, observed behavior, affected boundary, and evidence gaps. Never call a scanner finding reproduced or a provider-reported test independent QA without a matching owner receipt.
2. Identify the shared trust decision or state transition that makes the reported failure possible. Separate a confirmed source path from an inference based only on supplied prose. If source evidence is unavailable, keep every source-dependent conclusion conditional.
3. Compare at least two credible options when the evidence supports a real architectural choice: what changes, which failure each option prevents, residual risk, compatibility, performance, operational cost, rollout, and rollback. Include a smaller local fix when architecture change is not justified.
4. Recommend one next decision and the exact validation evidence needed before implementation. Save a Markdown option memo through `write_text_artifact_v1` only when admitted and requested; propose a draft work order through `create_draft_work_order_v1` only for an operator-reviewed implementation plan.

This is a design proposal, not a security scan, verified remediation, code change, or permission to deploy. Do not fabricate affected versions, exploitability, diagrams of uninspected code, or test outcomes.

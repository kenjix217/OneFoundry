# work planning

Use this procedure to turn an approved project goal or plan into reviewable work orders. If `create_draft_work_order_v1` is admitted for the current run, you may save a draft for an existing profile in this project. The operator reviews, marks ready, and starts work.

1. Read the project goal, requested outcome, constraints, and available profile names. Ask for missing authority or success criteria rather than inventing them.
2. Start with one end-to-end work order. Split only when another specialist must own a result, independent work can run in parallel, or QA or approval has a separate decision. Keep ordinary steps as acceptance criteria in the owning order.
3. For each proposed order, state the owner profile, exact deliverable, inputs, acceptance evidence, dependencies, and why a separate order is needed. Mark any unsupported tool or missing profile as a gap. Save a draft only when the exact profile exists and the role tool is admitted; read back its saved ID and draft status before claiming creation.
4. Sequence handoffs explicitly. A Researcher result can inform GTM, and Engineer evidence can go to QA. A handoff is an operator or Tool Gateway action; this document cannot perform one.
5. For email, publication, merge, deployment, cloud change, or other outbound action, identify the precise proposed action and wait for the OneFoundry approval inbox. Do not treat a drafted plan as approval.
6. Before saying the plan is executable, check that every proposed order has an owner, a concrete success test, and any required prerequisite. Report unresolved dependencies and unknown outcomes.

Output a compact table of proposed or saved draft work orders followed by acceptance criteria and open decisions. Preserve the source plan and its citations. Do not claim an order is ready or started until OneFoundry owner readback confirms that state.

# Project-wide agent automation decisions: design plan

The work-order delegation and chat action path in this plan is superseded by
`WORK_ORDER_SESSIONS_V2.md` on 2026-10-04. Project Automation rules remain a
separate feature.

Status: implementation in progress, 2026-10-03. The source is in the working tree; it is not installed or connected to a live model.

## Intended behavior

The one local operator can discuss a goal, a plan change, or ordinary work with an agent in **any supported project chat**. The agent decides whether the goal calls for one-time work, a new Automation rule, a change to an existing rule, disabling an obsolete rule, a clarification, or no action. The operator does not need to visit Automation, press a special action beside a message, choose an authoring agent, or name automation explicitly. The Chief of Staff can make the same decision or assign the work to another agent through the normal project workflow. An agent with a Chief-assigned task can make its own automation decision.

Rule management is a standing project capability for all active agents. There is no per-message grant or per-rule approval. A single **Agents may manage rules** project switch, on when the feature is enabled, can revoke agent writes. Agents save rule changes through the Tool Gateway; the Automation page remains the place to inspect, edit, pause, and see what happened. Email, publishing, merging, deployment, cloud changes, and other outbound actions retain their existing operator approvals.

The decision follows the goal: use an Automation rule for a durable trigger, schedule, or recurring handoff; use a work order for a one-time task. A changed goal may require revising or disabling a prior rule. The agent checks current rules before creating another one. If timing, trigger, target, or desired autonomy is unclear, it asks in the same chat and saves nothing yet. A model response saying it made a change is not completion; a saved version and readback are.

## Current source boundary

- App Task chats use `task_conversation_store.py` and record `tools_active: false`. The current source slice interprets one structured decision in the existing model response. A Chief decision may contain several bounded child assignments, each linked to the exact turn. Live role tools still use a provider-specific tool route; this decision path does not require that route.
- Discord and WeChat currently accept only a confirmed operator personal DM, bind it to a project and Chief of Staff work order, and forward it into that same task-conversation owner through `remote_channel_core.py`. Their actual live pairing and delivery have not been proved by this document.
- Incoming mailbox messages and watched documents are signals, not operator conversations. A future interactive channel must join the shared conversation path with a confirmed operator identity before it receives the behavior in this plan.
- Automation's `coordination_api.py` calls the Tool Gateway and `coordination_store.py`. Rule schemas already validate triggers, filters, schedules, target profiles, autonomy, and limits. Versions are immutable; revisions and enable changes use expected versions. The coordinator owns matching and fulfilment.
- The project has persisted `goal` and `desired_outcome` fields. The operator chose a separate project-wide plan record; `project_plans` now holds its body, version, and last actor. Work orders retain their own instructions and evidence. If a chat could mean the project plan or a specific work order, the agent asks which owner to change.

## Shared conversation path

1. **Normalize the turn.** Every interactive adapter submits to one project conversation owner: app Task chat with its selected agent; confirmed Discord or WeChat operator DM with the Chief; and later operator channels that implement the same contract. Save `project_id`, conversation/turn ID, target profile, source channel, external message ID if present, verified operator-origin status, and content digest. Preserve the channel's duplicate and unknown-outcome behavior. A raw email, document, webhook, or unauthenticated remote message cannot claim to be an operator turn.
2. **Give the agent the relevant state.** The current project goal, desired outcome, complete project-wide plan, work-order context, bounded relevant rule catalogue, supported trigger/filter catalogue, project timezone, and coordination status enter the model context after sensitivity checks. The current operator or Chief message remains the instruction; retrieved content and event details are labelled data. The agent does not receive credentials or an unrestricted project dump.
3. **Make one bounded decision in the conversation or agent run.** The agent returns a user-facing reply plus a strict action result. The current source slice accepts one command: `none`, `clarify`, `update_project_goal`, `update_project_plan`, `create_rule`, `revise_rule`, `disable_rule`, Chief-only `delegate_automation`, or Chief-only `delegate_team`. A `delegate_team` command contains several child work orders that save atomically and link to the exact decision. A rule command may include a versioned project goal update and a versioned project plan update; all changes commit together or none commit. Delegation saves draft children by default. When the Chief explicitly selects `auto_start` and project mode is Auto, text-capable work is saved ready with one launch intent for the existing bounded launcher; the reply says it has not run yet. A `code_change` child becomes ready for a separate coding runner and is never queued as a live-text job. A confirmed child outcome queues one bounded Chief follow-up in the conversation that created the assignment, supplied with fresh child evidence; a closed conversation blocks the follow-up. General combinations of independent commands and work-order instruction edits remain later slices. This is one provider-neutral structured-output attempt per turn, not a custom agent loop or a hidden second agent. Invalid structure produces no write and a visible unavailable result. A model connection that cannot produce this contract is reported unavailable for project changes; OneFoundry never silently swaps models.
4. **Apply through the owning gateways.** Before the turn or run completes, the Tool Gateway checks the project switch for rule writes, active project, actual assigned profile and execution, supported rule schema, same-project target, current rule state, and expected versions. It saves rule commands through the existing coordination store. A requested project goal change uses the project record's versioned update; a project plan change uses the new `project_plans` owner. A work-order instruction change must go through its work-order owner in a later slice. A chat reply or Automation rule is not a substitute for saving the intended plan/goal record. The agent cannot change coordination mode, tool policy, approvals, credentials, or project settings through a rule command.
5. **Return exact results in the same channel.** The reply says whether it created, revised, or disabled a rule, gives its name, trigger, target, autonomy, enabled state, and saved version, and links to the project Automation view in the app. If the agent chose one-time work or no automation, it says so briefly. The conversation timeline and Automation page both show the source turn, agent, channel, command, rule version, and readback. A remote reply follows that channel's existing outbound approval and delivery rules; a pending or failed reply does not erase a committed rule, and the app readback remains authoritative.

The Automation page's structured rule editor stays available for correction and inspection. It is not an entry requirement for agent-created rules.

### Examples

| Operator says in any project chat | Agent decision |
| --- | --- |
| “We need a competitor brief every Monday at 9 AM Eastern.” | Check existing schedules; create or revise one weekly Researcher rule if the project timezone can express the request. State its version and whether `COORDINATION_MODE` will let it run. |
| “Summarize this document now.” | Create or perform one-time work; do not create a standing rule. |
| “Change our project plan: QA should review every finished Engineer task.” | Save the project-wide plan version and create or revise a `work_order.done` rule for Engineer-to-QA handoff in one transaction; avoid a duplicate rule. |
| “Stop the weekly brief; the goal has changed.” | Locate the exact rule, disable it with expected-version checking, and report what was disabled. If several rules match, ask which one. |

## Ownership and durable contracts

| Owner | Required change |
| --- | --- |
| Shared conversation owner | Extend Task chat turns with trusted source-channel and operator-origin lineage. The app API and confirmed remote adapters call the same decision/apply path. Future channels implement this adapter contract before claiming parity. Keep normal replies available when no rule action is chosen. |
| Agent decision adapter | Ask the conversation's assigned agent for a strict reply/action envelope using its configured model. Provide a bounded rule catalogue and accept `none` as a normal outcome. Support clarification and goal/plan change choices. Avoid making an extra model call for every message. |
| Tool Gateway and domain stores | Execute agent-selected commands under the actual turn and profile. Reuse `RuleCreate`/`RuleRevise`, `coordination_store.py`, `ProjectStore`, and work-order owners. Enforce project switch, project-local IDs, expected versions, mode and resource limits, plus a configured maximum command count per turn. |
| PostgreSQL and events | Store a project/execution-unique action receipt with source channel, profile, decision, rule ID/version, goal version, plan version, outcome, and a digest of arguments. An execution is a conversation turn or a work-order run. Link rule changes to that exact execution. Keep raw private reasoning, secrets, and full inbound content out of events. |
| Chief and handoffs | The Chief may change rules itself during its chat or assign a child work order to another agent through a versioned Tool Gateway action. The child receives the goal and context through existing work-order lineage. In Auto mode, a configured bounded launch may start it; otherwise it remains draft or ready for the operator. A Chief instruction does not grant global settings or outbound authority. Starting that child is recorded separately; do not claim an unstarted assignment was executed. |
| Coordinator and Automation UI | The coordinator continues to consume saved versions only, enforcing pause, `off`/`draft_only`/`auto`, dedupe, daily caps, and chain depth. Automation displays human and agent edits with exact lineage and lets the operator correct or disable a rule. |

Use one stable `(project_id, execution_kind, execution_id)` identity for the current bounded decision. Commit rule, goal, and plan writes with one success receipt atomically. If persistence or provider outcome becomes unknown, read back that identity before allowing another attempt. A replayed Discord/WeChat message or chat retry must not create a second rule. Any future expansion to several independent commands needs indexed receipts and explicit partial-outcome handling.

## Decision boundaries

- A recurring goal can justify a rule even when the operator does not say “automation.” The agent must explain the rule it chose. If a one-time instruction is sufficient, it should not create a schedule or event rule.
- Only a verified operator conversation or an actual Chief/agent work-order turn can drive this path. Untrusted mail, documents, web pages, and signal payloads are context, never a new instruction or a claimed operator identity. The project switch blocks new agent rule writes from every channel immediately.
- Creating an enabled rule can cause future work. The agent defaults to `draft` work orders when autonomy is unspecified. `ready` and `auto_start` must be supported by the expressed goal and remain bounded by the project's configured coordination mode and existing daily, chain, budget, and review gates. No rule may approve its own outbound effect.
- If a project timezone cannot express the requested schedule, or the plan/goal target is ambiguous, the agent asks in the current channel. It does not invent a timezone or silently overwrite a different plan record.
- Rule creation, revision, and disabling must preserve project scope, valid target profiles, immutable prior versions, conflict detection, and actor attribution. A disabled rule is inserted disabled in one transaction, so it cannot fire between create and disable.

## Delivery slices and acceptance

1. **Conversation contract.** Trace every current interactive entrypoint and add typed source/identity lineage. Keep current Task chat and confirmed Discord/WeChat messages working. Test duplicates, unknown turns, cross-project attempts, unconfirmed remote identities, and third-party inbound content.
2. **Agent decision and state.** Add the provider-neutral reply/action envelope, bounded rule and project context, and a no-action path. Test a recurring goal, one-time task, changed goal, duplicate existing rule, ambiguous schedule, unsupported model, and malformed output. Verify the same behavior on a normal Task chat turn without an Automation-page action.
3. **Gateway writes and readback.** Add project-wide standing admission, exact turn receipts, direct create/revise/disable, and goal/work-order owner updates where requested. Test normal writes, stale versions, invalid fields, target mismatch, switch-off, replay, partial multi-command outcome, and uncertain commit against disposable PostgreSQL.
4. **Chief and channels.** Exercise the Chief deciding itself and assigning a child work order that another agent actually runs when project mode allows, with a truthful draft/ready state otherwise. Prove an app Task chat turn and confirmed Discord and WeChat DMs take the shared path, with channel-specific reply status preserved. Any future chat channel uses the same acceptance contract before being advertised as supported.
5. **Runtime acceptance.** Run repository format, lint, strict typing, full regression, migration, affected integration, and real-model checks. In a disposable project, verify desktop/mobile app chat, persisted rule/version/lineage, a fired signal and expected work order, an existing-rule revision, and no-rule choices. Verify a connected remote channel live only when its real pairing and credentials are available; otherwise report that channel gate as unexecuted in `PROGRESS.md`. Do not deploy, migrate shared data, or start paid provider calls as part of this design document.

Completion requires a saved rule or explicit no-rule decision tied to the exact conversation turn, plus database/API readback and coordinator behavior for rule cases. Model text alone is not completion evidence.

## Working-tree implementation status

- App Task chat and confirmed Discord/WeChat DM turns now carry an immutable source identity; system triage stays outside the operator-decision contract. Normal chats ask the assigned profile for one structured rule/goal/plan decision in its existing text-model call. Live text work-order runs use the same decision and save path. Chief chat can save a draft child assignment or queue one ready child for the existing bounded Auto launcher; the child can create a rule on its own run. The Tool Gateway validates accepted commands through the existing rule store, versioned project goal, and separate versioned project plan, then records a turn- or run-bound receipt. A replay cannot create a second rule. The Automation page has a project-wide agent rule switch and shows the last agent action for a rule. Task chat Assignment lets the operator read or correct the project plan.
- Focused fake-provider tests cover create, revise, disable, stale version, project goal, project plan, an atomic goal/plan/rule decision, no-rule, switch-off, remote channel source, replay, and pairing change during generation. This proves the local owner path, not real provider compliance or live Discord/WeChat delivery.
- Still needed for the full design: work-order instruction edits when explicitly requested, several independent commands, live-model proof, and live remote pairing/delivery acceptance. Coding-agent runs and other non-text execution modes do not yet use this text decision contract.

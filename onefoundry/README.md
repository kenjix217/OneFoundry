# OneFoundry local app

OneFoundry is a localhost workspace for a Chief of Staff and configurable AI
specialists. Give Chief an objective, follow delegated assignments, inspect saved
results and files, and review outward actions. This guide covers setup and
operation; the [project overview](../README.md) introduces the workflows and
architecture.

Role agents can use supported cloud model APIs or locally hosted Ollama models,
with an account/model chosen per profile. Coding work uses separate Codex CLI or
Claude Code workers through the Execution Gateway and its supported execution
paths. When working directly in Codex, the Company Memory plugin can retrieve
approved project/company knowledge and propose explicitly selected excerpts for
local review. See [models](#model-account-configuration), [delegated coding](#delegated-coding),
and [company memory](docs/company-memory.md).

The [architecture overview](docs/ARCHITECTURE.md) describes current owners and boundaries. Versioned packaging, installation, software updates, and rollback are documented in [docs/RELEASE.md](docs/RELEASE.md). The installed release path is separate from this source checkout. [VERSION](VERSION) and [CHANGELOG.md](CHANGELOG.md) describe the source; [PROGRESS.md](PROGRESS.md) and the [maintenance acceptance record](docs/SELF_EXTENSION_COMPLETION.md) identify what was verified in each release.

OneFoundry is the product name, source directory, Python package, PostgreSQL database, and Docker Compose project. For a versioned installation, use the archive-backed `onefoundry update` procedure in [docs/RELEASE.md](docs/RELEASE.md); it checkpoints the declared persistent volumes, applies migrations, checks readiness, and attempts recovery on failure. A one-time migration from an older development Compose project needs an explicit data and artifact cutover plan. Browser storage migrates saved project selection and unresolved request keys when the new UI reads them.

The [Chief workspace guide](docs/CHIEF_COMMAND_WORKSPACE_DESIGN.md) describes the primary conversation flow. The earlier [operator workspace guide](docs/UI_REDESIGN.md) remains a reference for optional records and configuration pages.

## Integrations, tools, plugins, and skills

Open **Integrations** from the project sidebar. Integration Hub and Tool Foundry
use the existing Tool Gateway, including its project scope, profile grants,
approvals, and saved events.

1. **Connections:** configure a project API or MCP connection, inspect readiness,
   and manage signed incoming webhooks. Endpoint settings and protected
   credentials are separate from a reusable package.
2. **Skills & Tools:** search the catalog, inspect exact package versions and
   prerequisites, and bind saved connections to declared package slots. Configure
   from a skill or tool opens the same shared project connection editor.
3. **Tool Foundry:** write a skill procedure, import a package ZIP, or start from a
   Python/API/MCP/outbound-webhook template. Save an inert draft, inspect it, and
   request activation of its exact version. New connection templates become
   available after saving their package draft.
4. **Team:** review tool grants and pin accepted skill versions to a profile.
   Accepting a skill or activating a package does not grant its tools to agents.

An admitted agent can propose a skill draft; the operator reviews its exact
instructions and prerequisites before accepting it. Python and pinned local MCP
execution require the separate isolated supervisor. Generic API/MCP calls and
outbound delivery retain exact-call approvals. Signed incoming webhook receipts
feed the existing automation pipeline; they do not claim a resulting job is done.

Build reusable packages with the [Python SDK](sdk/python/README.md) and
[account-brief example](sdk/python/examples/account-brief/README.md). See the
[runtime/settings reference](docs/UNIVERSAL_EXTENSION_RUNTIME.md),
[supervisor setup](docs/EXTENSION_SUPERVISOR.md),
[design](docs/UNIVERSAL_EXTENSION_DESIGN.md), and
[implementation/acceptance record](docs/UNIVERSAL_EXTENSION_IMPLEMENTATION.md).
Codex/Claude adapters support the documented inert subset with compatibility
reports; foreign hooks, commands, and permissions never activate on import.

## Work through Chief

Settings uses a single **Settings page** selector for configuration and historical views. **Customize → Color theme** applies to Chief, Settings, forms and side panels. `frontend/src/theme-palettes.css` owns every UI color; other stylesheets consume its semantic roles and must not define colors or color fallbacks. `themeOwnership.test.ts` enforces this across every preset.

Open a project and give Chief an objective in the conversation. The first message saves one root job and queues the configured team worker; opening **New conversation** alone creates no draft. Chief owns delegation, bounded recovery, QA corrections and verified local delivery. Click an agent's name for its assignment, supplied context, saved public conversation and verified files. Technical receipts remain in **Details & earlier attempts**.

**Current work** shows working and queued turns, missing results, saved files, and the next available action. A recovery action opens the affected Chief or specialist session. Choose **Reconcile saved actions** to check exact persisted receipts; a confirmed saved terminal report clears its execution hold while retaining the historical uncertain provider outcome. If the outcome still cannot be proved, review the saved actions before recording a reasoned abandonment. Neither action replays work or approves an outbound effect. Saved-file cards use the producing task title and open the exact artifact. Completed work that requires operator acceptance links to its existing review controls. The read-only `GET /api/projects/{project_id}/chief-workspace/{order_id}/progress` endpoint projects these counts, blockers, and actions from the existing owners.

Saved reports open as readable text after verified readback. **Copy report** and **Save a copy** preserve the exact saved text; expand **Exact saved text** to inspect it. Opening a report holds automatic chat following while you read. Scroll to the bottom to resume following.

Use the copy and edit icons on operator or agent messages. Edit loads the text
into the composer; Send saves a new message and keeps the original history.
Chats follow new messages and progress while you are at the bottom; scrolling
up lets you read earlier messages. Agent action activity starts collapsed, with
public messages and concise failure notices visible. Expand it for saved tool
records. Each sidebar conversation has an Archive icon. Archived conversations
offer Restore and recoverable deletion to Trash. Archive pauses future chat
turns; active work may still finish.

The composer preserves long pasted text without the former 16,000-character
cutoff. Chat APIs accept up to 1,000,000 characters, subject to the configured
context budget and the provider's model capacity. Rejected submissions keep the
unsent draft; a saved message can still receive a failed or unknown provider
outcome. A long first message remains the task's required objective in later
team context, including after recent history is paged out. Finite team context
budgets reject a turn that cannot include the required objective or latest
message in full. Legacy task chat retains its existing live-text byte budget.

The conversation opens with the composer focused and **Chief** selected in the **Conversation agent** dropdown. Select a project agent, including a custom profile, to start a direct conversation using its configured model, tools and memory scope. Switching agents starts a new conversation without changing the owner of saved history; an unsent message is retained. No work order or model turn is created until Send. Direct conversations retain operator review and the existing outbound/unknown-outcome holds; Chief remains the coordinator for delegated team work.

For a known stopped job, message Chief in the same conversation to continue. Prior attempts and accepted work remain saved. Unknown effects and pending outbound approvals allow inspection and discussion while their owner resolves the exact outcome; a message does not acknowledge uncertainty or authorize an external effect. New internal jobs finish after accepted work and independent QA. Historical operator-review and coding/outbound jobs retain their existing completion owner.

The conversation menu offers **Rename**, **Pause/Resume** and **Archive/Restore**. Pause and Archive hold future turns; a running bounded turn may finish. Archive preserves history. **Settings** contains optional configuration, activity, approvals and **Legacy records**. Missing model/worker setup saves your direction with a clear setup response, without claiming that work has started.

## First project without AI

The following manual recording and legacy task controls remain optional under Settings. **Customize** is available on configuration pages for saved browser preferences.

After starting the app below, open `http://127.0.0.1:8765/` and click **Create project**. Enter a name; OneFoundry saves a Chief of Staff and five specialist profiles. In **Settings → Project setup**, save the project brief, fill any missing starter instructions, then choose **Continue without AI or a repository**. Save a draft work order assigned to a role. In **Work orders**, open **Manage** for that draft, choose **Mark ready**, then **Start manual run**. In **Activity**, open the run, enter a reason, and choose **Record outcome**. Return to Setup to see the saved outcome. This path makes no model or coding-agent call. Profiles are assignment labels until a model is connected.

**Work orders** is a searchable project queue. **Open task** shows a task workspace with Conversation, Progress, Results, and Assignment tabs. A work order can have several named chats; **New chat** starts a separate history with its assigned agent, and previous chats stay readable. Text chat shows the outgoing message while the model works and asks for a brief plan, findings, and next step in its visible reply, without exposing private model reasoning. A failed team-assignment proposal is labeled as unsaved; the reply alone does not create work. Activity uses saved events, and Results uses saved run outcomes. Expand **Actions in this run** for available runner-observed commands, bounded output, test receipts, and saved patch/log files. The trace is labeled partial because coding-provider internal tool calls and intermediate agent updates are not captured by the installed external runner. Older attempts may have no command trace. Existing work-order start, edit, file, and assignment controls remain under **Manage**; task Assignment links there.

**Settings → AI connections** and **Project repository** are optional. A repository is needed only for source-based checks or later coding paths; it is not needed to create a project or record manual work. The browser cannot grant a Docker container access to a new host folder. Use the local repository command below only when you want a checkout in OneFoundry.

## Model account configuration

The Models API shows 61 choices adapted from DistrictAI's directory plus OneFoundry aliases. Forty-two text routes have a OneFoundry connection path: OpenAI Codex account login, OpenAI, Anthropic, Gemini, xAI API keys, compatible API providers, and keyless local Ollama. Nineteen entries still lack a OneFoundry adapter and remain disabled. Grok account sign-in uses the public native OAuth client by default and remains separate from the xAI API-key connection. These choices are not 61 independent runtimes. Explicit discovery fills a model catalog for profile selection. In Team → Edit profile, **Refresh [account] models** requests that account's current catalog and updates the picker; select a new model and save the profile to change its binding. The same provider request is available as **Discover models** in Settings → AI connections. A provider account cannot be removed while a profile uses it. A failed refresh retains saved model names but marks them unavailable.

The app keeps API keys and Codex/Grok device and refresh credentials only in `MODEL_SECRET_ROOT` (default `/model-secrets`), an app-owned directory with mode `0700`; each account file is mode `0600`. Compose initializes a dedicated named volume. Credentials are never returned by the API or saved in PostgreSQL. Device sign-in returns only the short user code and verification URL to the browser. For direct installations, create the directory under the app UID before startup. `/health/ready` checks that directory and the model tables.

Codex account cards read the saved credential expiry and show **Reconnect required**
with a visible explanation when the login expires or renewal is rejected.
**Reconnect account** starts device sign-in on that same account, preserving agent
model bindings. **Complete login** checks the displayed sign-in; automatic polling
also continues at the provider's interval. **Refresh status** rereads local account
state without requesting a new login or calling a model. Saved model names remain
unavailable while disconnected; after reconnecting, use **Discover models** to
refresh their availability. A failed request for a fresh sign-in code preserves
the previous credentials. Reconnecting does not restart stopped conversations or
change the developer's local Codex CLI login.

If account removal returns 503, reload the account list before trying again: the database deletion may have completed. When the account is gone, restart the single local app service to reconcile any remaining orphan key file.
If account removal commits but file cleanup fails, the API reports an unknown failure and startup removes the orphan UUID key file after reading the account table. This recovery assumes one OneFoundry app instance owns the secret volume.

Model-list endpoints for the original cloud providers are fixed to their HTTPS URLs through validated settings. Additional compatible API endpoints come from the bundled provider directory. Codex device login and model discovery adapt the existing DistrictAI and JintellarCore account-runtime paths; `CODEX_DEVICE_TIMEOUT_SECONDS` (60–1800, default 600) bounds sign-in; `CODEX_AUTH_EXCHANGE_TIMEOUT_SECONDS` (10–120, default 60) bounds the one-time OAuth exchange separately from model discovery; and `CODEX_CATALOG_CLIENT_VERSION` (semantic version, default `0.160.0`) identifies the catalog client. OpenAI gates catalog entries by this version; older explicit overrides can omit newer models even for a connected account. The configured default is maintained independently of installed coding CLIs; discovery uses only the account’s fresh provider response, never the local Codex cache or a bundled model list. Discovery failures retain saved rows but mark them unavailable until a successful refresh. Grok account sign-in uses xAI's published native-client device flow. `XAI_OAUTH_CLIENT_ID` defaults to the public client identifier published in [xAI's login configuration](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-login/src/config.rs); it is not a secret. An explicit empty value disables Grok sign-in; environment values override the default, and explicit Settings arguments override the environment. `XAI_OAUTH_ISSUER` and `GROK_ACCOUNT_BASE_URL` default to, and accept only, `https://auth.x.ai` and `https://cli-chat-proxy.grok.com/v1`. The device page displays only the short code and verification URL, resumes after reload, respects provider polling and slow-down intervals, and offers **Start fresh sign-in** on the same account when a code expires or an exchange is uncertain. A saved token can complete its interrupted account update without another provider request. **Sign in again** reconnects a bound account without deleting its profiles; discover models again afterward. Device grants and refresh-token rotations are serialized; interrupted exchanges stop automatic replay. Grok account text and SDK team turns use the documented streaming Chat Completions proxy and CLI authentication headers, with configured output bounds and storage disabled. This is distinct from the Grok API-key provider and does not connect a Grok coding CLI. Real account login, renewal, model discovery, and inference still require operator acceptance. Keyless Ollama accounts accept only an HTTP origin on `localhost`, `127.0.0.1`, or the Compose service name `ollama`, with an explicit port. Discovery settings are `MODEL_DISCOVERY_TIMEOUT_SECONDS` (1–15, default 5), `MODEL_DISCOVERY_MAX_PAGES` (1–10, default 5), `MODEL_DISCOVERY_MAX_RESPONSE_BYTES` (1024–2000000, default 1000000), and `MODEL_DISCOVERY_MAX_MODELS` (1–1000, default 500). Discovery makes a request only when explicitly refreshed; profile saves and page loads use the saved catalog.

Profile instructions accept up to 50,000 characters in Team and the project profile API. The editor shows the count and rejects over-limit text without clipping it; PostgreSQL stores the saved text intact. Long profiles still count toward the live-text prompt byte budget, so a run may be refused before provider egress if the complete prompt does not fit.

Live text configuration is bounded by `LIVE_TEXT_MAX_PROMPT_BYTES` (1024–1000000, default 96000), `LIVE_TEXT_MAX_OUTPUT_TOKENS` (1–8192, default 512), `LIVE_TEXT_MAX_OUTPUT_BYTES` (1024–16000, default 16000), and `LIVE_TEXT_TIMEOUT_SECONDS` (1–120, default 30). `SKILL_AUTO_MAX_COUNT` (0–10, default 3) and `SKILL_AUTO_MAX_CONTENT_BYTES` (0–48000, default 16000) bound automatically matched procedures; zero disables automatic matching while explicit profile pins remain. The total prompt limit still applies. `LIVE_TEXT_TOOL_MAX_TURNS` (2–8, default 3) bounds SDK continuation for an OpenAI API-key role with admitted tools. `ROLE_CONTEXT_MAX_ITEMS` bounds each project-context tool list (1–20, default 5); the output byte limit also applies. The prompt limit counts UTF-8 bytes of the outbound instructions and work prompt together, including selected skills; excess fails before a run or provider call. `LIVE_TEXT_OPENAI_BASE_URL`, `LIVE_TEXT_ANTHROPIC_BASE_URL`, `LIVE_TEXT_GEMINI_BASE_URL`, and `LIVE_TEXT_GROK_BASE_URL` accept only their official HTTPS API base URLs. These settings do not themselves enable live execution. Task chat uses the same text prompt/output bounds and its own `TASK_CHAT_TIMEOUT_SECONDS` (1–600, default 120) provider deadline; this is a cap, not a delay. Codex account Task chat can save and display up to eight completed provider-authored public progress summaries during a turn. It never exposes raw reasoning or treats an update as a completed reply. Other providers may supply only the final reply. `TASK_CONVERSATION_MAX_TURNS` (1–1000, default 100) bounds recent conversation context and each saved-history page. It does not cap total saved turns. Task chat can load earlier pages while continuing the same work order. Before team activation, ordinary Task **Send** makes one discussion-only provider text call; it cannot apply agent actions or launch work. The legacy API defaults remain compatible for remote and saved action requests, but rejected proposals are clearly marked rejected and show content-free field diagnostics in Reply details. On an eligible root Chief task, **Start work** saves the current message (or uses the saved assignment), admits a draft, preserves earlier chat, and queues the existing SDK team workflow atomically. Review Execution capabilities for configured repository-read and coding limits; Start work grants no new permission. In the active team session, **Send to agent** explicitly queues another work turn. The legacy action API can still save structured project goals, plans, Automation decisions and bounded Chief assignments. A rule command may carry goal and plan updates in one atomic decision. The separate project-wide plan is readable and editable in Task chat Assignment and at `GET/PATCH /api/projects/{id}/plan`; changes use `body` and `expected_version`. Operator messages and final replies stay in conversation tables. Bounded public progress summaries are saved as attributed activity events and read back with their exact turn. An unknown turn pauses further Sends until the operator selects **Continue conversation**. That action records an append-only acknowledgment and allows a new message in the same work order; it never resends or changes the unknown turn. Only confirmed replies enter later prompt history. Provider cost may be unavailable. `AGENT_AUTOMATION_CONTEXT_MAX_ITEMS` (1–50, default 8) bounds the project agent and rule catalogue sent to a chat or live text run, and the number of team assignments in one decision; `AGENT_AUTOMATION_GOAL_MAX_CHARS` (100–4000, default 500) bounds each project goal field and rule instructions in that context. The separate plan is bounded to 4000 characters and supplied complete. A rule catalogue above the limit blocks agent rule creation and revision; oversized saved goals block agent goal updates, and rule instructions longer than the text bound block agent revision. Agent rule changes require the project Automation switch; outbound approval gates still apply.

Team work-order sessions default enabled (`TEAM_WORKER_ENABLED=true`); a work order must still be admitted into team mode. Explicit false remains supported. Each agent turn uses that agent's own model account through the installed Agents SDK, so agents can use different providers and switch between turns. Concurrent capacity and no-progress safeguards hand control to the operator: `TEAM_MAX_DELEGATION_DEPTH` (default 2), `TEAM_MAX_ASSIGNMENTS_PER_ORDER` (8 unfinished assignments), `TEAM_MAX_PLAN_REVISIONS` (3), `TEAM_MAX_CHIEF_DECISIONS_PER_ORDER` (6 automatic decisions without new confirmed result evidence or an operator checkpoint), `TEAM_MAX_MODEL_CALLS_PER_TURN` (8), `TEAM_TURN_TIMEOUT_SECONDS` (300, shorter than `ONEFOUNDRY_MAX_ELAPSED_SECONDS`), and `TEAM_MAX_OUTPUT_TOKENS` (4096; the Codex account route accepts no output cap). A turn the provider provably never processed and that saved no action is retried once after `TEAM_RETRY_DELAY_SECONDS` (30); unknown outcomes are never retried.

The project Skill Library stores procedure text in immutable numbered versions (maximum 16,000 UTF-8 bytes). Create a skill with `POST /api/projects/{id}/skills`, then add versions at `/skills/{skill_id}/versions`. List both through GET at those paths; GET `/skills/{skill_id}/versions/{version}` reads one exact revision. Optionally pin a profile to an exact version with `PUT /api/projects/{id}/profiles/{profile_id}/skills/{skill_id}` using `{"version": 2, "expected_binding_id": "<current binding id>"}`; use `expected_binding_id: null` for a new pin. Remove it with DELETE at the same path and `?expected_binding_id=<current binding id>`. The binding ID changes on every save; stale writes return 409 even if the selected skill version changes away and back. Live text runs and Task chat automatically match the complete project library by task metadata, then supply only the bounded relevant procedure bodies to the model. Run detail and turn readback show exact selected versions and hashes. Manual, synthetic, and external coding runs save pinned version metadata only; they do not deliver full procedures to a model or coding CLI. A skill never changes allowed tools, autonomy, or approval requirements.

For a live text run, discover a text model under a connected Codex account, supported API account, or local Ollama account and bind it to a Researcher, GTM, or custom profile with instructions. A ready work order makes one bounded provider call, except that an OpenAI API-key profile with admitted tools uses the installed Agents SDK for bounded tool-call continuation through the Tool Gateway. No other provider text transport advertises role tools. When a profile requests tools that the chosen route cannot execute, launch returns 409 before a run or provider call is made; an empty tool list permits a text-only call. Legacy labels such as `work_order_create` and `memory_search` are not registered Tool Gateway IDs and must be replaced with actual IDs through the profile editor. The run saves the task/profile/account/model snapshot, retrieved memory context, output, token usage, and events. Provider-reported cost is saved when supplied; otherwise cost is unknown. A `done` live text run confirms a saved model response; the parent work order still requires matching deliverable evidence or explicit operator acceptance and can remain `needs_review`. No pricing estimate or automatic retry is made. The SDK route has offline scripted-model tests; live account tool-call acceptance remains unproved. A Models-page Codex text connection does not authenticate the separate Codex coding CLI. For a Codex account model, Team offers only reasoning efforts advertised by that account's most recently discovered catalog; refresh discovery to populate or update them. Setup also offers separate reasoning choices when assigning Researcher and GTM. The selected effort is checked again when a text run starts and recorded with the run. The Models page's text label describes OneFoundry's current text-input/text-output route, not the model's full modalities; image and video inputs are not implemented there.

The Tool Gateway admits project and run scoped role reads with saved and current profile allowlists, typed input, bounds, and hash-only intent/outcome events. The existing context reads remain `current_work_order`, `project_brief_v1`, `recent_project_work_v1`, `run_evidence_v1`, `coding_evidence_v1`, and `approved_memory_v1`. `repository_file_v1` reads bounded UTF-8 text from a saved commit; `repository_tree_v1` takes `source_id`, optional `directory` (empty for root), and optional `after` (a path cursor); it pages committed safe file/directory entries by the run item limit and returns `has_more` and `next_cursor`. `repository_file_range_v1` takes `source_id`, `path`, and a zero-based character `offset`; it returns `text`, `next_offset` (null at EOF), and the complete screened document SHA-256 and byte size. Pages are UTF-8 bounded by half the live output limit; full files are bounded by `INPUT_FILE_MAX_TEXT_BYTES`. `coding_artifact_text_v1` reads receipt-verified saved diff or log text. Granted team reads use `TEAM_REPOSITORY_READ_ENABLED`; static browser inspection uses `BROWSER_STATIC_ENABLED`. Generic live-text source/diff and GitHub PR exclusions remain. Missing or cross-project records do not expose content. A changed tool contract needs a new ID because snapshots pin IDs. A `SKILL.md` does not grant these permissions.

Team turns run sequentially. After delegation the Chief finishes its turn, allowing queued specialists to run. `read_dependency_result` returns `pending` for waiting assignments, `blocked` for rejected work and `canceled` for retired branches. A saved availability observation remains unchanged after a later result; a fresh tool call reads the current state. Blocked QA reads include paged, hashed review feedback tied to the saved review receipt, without satisfying the assignment. Every specialist input must be declared in `depends_on`; mentioning an ID in instructions grants no access. The Chief carries rejected QA feedback into rework instructions and retires the inactive rejected branch before a new review.

During an active native team turn, the canonical main Chief has intrinsic read-only oversight tools: `read_project_status` reads the project goal, plan and all order states; `read_work_order` pages any order's complete nested workflow, assignments, dependencies, decisions, runs/coding receipts, artifacts, approvals and event metadata; `read_agent_session` reads any project agent's public saved messages, attempts and tool receipts, including closed and failed branches. Work-order status does not remove these read tools. Specialists retain their declared input scope. Reads do not reopen orders, launch specialists, accept results, grant repository tools or approve outbound actions. A new execution turn still requires the existing worker, project and lifecycle gates.

Inspection returns JSON as exact content pages. Keep `created_before` on subsequent pages; reconstruct `next_content_offset` pages with `expected_sha256=body_sha256`, then advance record `offset` using `next_offset`. The cutoff excludes newly created records and the inspection's own growing event stream; statuses are observed per page. `inspection_state_changed` requires restarting that record page with fresh content, rather than joining contradictory states. Sensitive fields are held while their record's safe status remains visible. The project Chief inbox receives complete nested assignment/attempt counts for each candidate order; it remains a bounded summary decision endpoint. Exact session inspection belongs to the work-order team's native Chief tools, with every read recorded in schema 0078.

`github_pr_read_v1` requires a saved GitHub source, an active role run with the tool allowed, and a one-use operator approval. Create a proposal with `POST /api/projects/{project_id}/runs/{run_id}/github-pr-read-approvals` and `{"source_id":"<uuid>","number":7,"idempotency_key":"<uuid>"}`. Approve it in the normal inbox. A trusted run-bound caller can then invoke the tool with `{"approval_id":"<uuid>"}`; it checks the source and approved base revision before and after one bounded official GitHub API read, and records a hash-only result. `GITHUB_PR_READ_APPROVAL_MINUTES` (1–60, default 15) limits the approval lifetime. Approval, saved-source access, and result validation are separate checks; no role can mint its own approval. The synchronous live SDK does not advertise this PR tool until an operator approval wait/resume flow can deliver the approval ID. This endpoint and tool have synthetic and mocked tests, not a live GitHub account acceptance result.

Static browser inspection is a default-off, operator-approved HTML/CSS fixture path. The run's assigned built-in Researcher or QA profile needs `browser_static_inspect_v1` in its saved and current tool list. The operator proposes and approves the exact fixture in **Activity** and **Approvals**, then dispatches one job; a separate host bridge performs networkless inspection and returns bounded text evidence to Activity. QA can use an active manual run. The live model SDK does not initiate this tool. Setup and recovery instructions are in [Static browser inspection pilot](docs/STATIC_BROWSER.md).

`decimal_calculate_v1` performs bounded string-decimal arithmetic. `write_text_artifact_v1` saves up to 65,536 UTF-8 bytes of plain text, Markdown, or CSV in a private persistent workspace; it returns metadata only and records hash-only tool events. Both require the active run's saved and current profile allowlists. Set `ARTIFACT_WORKSPACE_ROOT` to an absolute dedicated directory (Compose defaults to its private named volume). In **Activity**, open the run to see saved artifact status and preview a ready artifact; the preview verifies its recorded path, size, hash, and file identity before showing text. The operator API also lists `GET /api/projects/{project_id}/runs/{run_id}/workspace-artifacts` and previews `GET /api/projects/{project_id}/runs/{run_id}/workspace-artifacts/{artifact_id}`. These tools do not render PDFs, slides, images, charts, or spreadsheets.

`create_draft_work_order_v1` is an internal workflow write for an active run whose saved snapshot and current profile both allow it. It accepts an existing same-project profile ID, title, and instructions; saves one `draft` work order; and returns the saved ID and status. Repeating a call ID cannot create another draft. The role cannot mark it ready or start it. A profile's tool allowlist is set in **Team**; a skill document alone does not enable this action.

`request_qa_review_v1` accepts the same project's built-in QA profile ID and a bounded note. It records a role-attributed request in the current run timeline, with a hash-only tool receipt. It does not assign QA, hand off, change run status, or approve the result. The operator reads the request in **Activity** and decides the next action.

`github_pr_comment_v1` prepares a whole-PR issue comment for a saved GitHub source; the PR head is observed, but a commit change can race the posting request. An active run needs the tool in both its saved and current profile allowlists. The role tool only creates a pending proposal, and the live SDK excludes it until approval wait/resume exists. An operator can also prepare the proposal in **Approvals**. Review the exact text, approve it, check saved status, and explicitly choose the one-shot **Post exact comment once** action. Unknown outcomes have no POST retry; an acknowledged comment can be read back once. The account credential remains in OneFoundry's private store. This path has fake-transport tests and no live GitHub acceptance.

Researcher public-web tools are separate run-bound reads: `public_web_search_v1` returns bounded search results, and `public_page_fetch_v1` returns bounded text from one public HTTPS URL returned by a successful search in the same run. The public-web policy defaults enabled (`PUBLIC_WEB_ENABLED=true`). Explicitly allow the tool IDs on the Researcher profile before starting a run; the saved run snapshot and current profile must both allow them. Search additionally requires `PUBLIC_WEB_SEARCH_ENDPOINT` to be a trusted SearXNG `/search` JSON endpoint, either public HTTPS or the exact internal `http://searxng:8080/search` address for an operator-managed service. OneFoundry does not start SearXNG itself. [SearXNG's API](https://docs.searxng.org/dev/search_api.html) requires the instance to enable JSON output. `PUBLIC_WEB_TIMEOUT_SECONDS` (1–15, default 8), `PUBLIC_WEB_MAX_RESPONSE_BYTES` (1024–2000000, default 65536), `PUBLIC_WEB_MAX_TEXT_CHARS` (256–16000, default 4000), and `PUBLIC_WEB_MAX_RESULTS` (1–10, default 5) bound each call. Page fetch returns `text_truncated` when its bounded text is an excerpt; a truncated excerpt cannot prove the whole page. The live output-byte limit also applies to the complete tool result, including source metadata, so a fetched text excerpt may be shorter than `PUBLIC_WEB_MAX_TEXT_CHARS`. Public HTTPS fetch rejects local/private destinations, redirects, credentials, proxy use, compressed/binary pages, and oversized responses. The Tool Gateway stores only hashes, status, and fixed content-free failure codes in events; team callers receive the same code on first call and replay. An OpenAI API-key live text role with the saved and current Researcher allowlist can call these tools through SDK continuation. Other provider transports remain tool-free; live account acceptance remains unproved.

The native self-extension workflow uses `repository_code_v1` for an exact

withheld. These artifacts support a reviewed repair and remain failed evidence:
they cannot satisfy Engineer completion, independent QA admission, or activation.
Unknown provider outcomes and rejected scope/protected-content changes retain no
candidate. Repair requires a fresh approved target; the failed attempt is never
silently replayed.

Engineer work orders now have a separate `external_code` path through the Tool Gateway and Python Execution Gateway. It records an exact Codex CLI or Claude Code attempt, dispatches a fixed disposable repository job, and reconciles a runner-owned receipt with source diff, tests, session ID, and usage when reported. The older scripted Engineer→QA repair remains under Diagnostics as an offline fixture. Migration `0021` keeps external attempts and artifacts separate from that fixture.

`EXTERNAL_CODE_ENABLED` defaults to `true`; set it to `false` to disable the gateway. Enablement does not launch a job or bypass runner capability, work-order, provider or approval checks. The older trusted-host mode uses a separate local worker, a disposable calculator repository, and the operator's existing Codex CLI or Claude Code login. It does not isolate the CLI from the operator's host account. The app's Codex model connection and CLI login are separate stores. Both adapters completed a disposable live pilot. This worker requires explicit operator setup and is separate from the isolated maintenance path above. The Claude adapter requires the supervisor to admit an installed CLI version supporting its restrictive flags; no host Codex or Claude settings are read or changed.

Native Chief and direct-agent conversations use the durable team session and

## OneFoundry organization records

`ONEFOUNDRY_BUSINESS_MODE` defaults to `off` and accepts `off`, `records`, `manual`, `event`, or `inbox`; invalid modes fail startup validation. `off` hides Organizations and its project routes. `records` enables project-scoped district evidence, human claim review, qualification, and allowed-action readback. `manual` adds operator-approved company facts, linked research and draft work orders, pinned context, budget admission, candidate import from confirmed run output, and cited draft revisions. `event` adds one durable internal continuation: after qualification, a separate coordinator creates one ready Sales draft order. It does not start a run or contact anyone. Use `event` only after migration `0043_coordination_core`. The `onefoundry-coordinator` Compose service now starts by default; it runs when `event`, `inbox`, or `COORDINATION_MODE` is enabled and exits cleanly when none is. `inbox` adds a read-only operator inbox and owner-derived outcomes on top of event mode; it uses the same separate coordinator and never starts a run or sends contact. Reviewed research counts districts with a completed linked research run and an operator-reviewed claim. Draft revisions are counted as saved rows. Unknown usage is shown as unavailable. The sample and Compose default stay `off`. A file-backed claim still requires a matching extracted input-file chunk.

Manual workflow limits use `ONEFOUNDRY_MAX_LINKED_ORDERS` (default 2, 1–8), `ONEFOUNDRY_MAX_MODEL_ATTEMPTS` (2, 0–8), `ONEFOUNDRY_MAX_PUBLIC_WEB_CALLS` (0, 0–20), `ONEFOUNDRY_MAX_CONTEXT_BYTES` (`unlimited` by default; explicit 1,024–32,000-byte limits supported), `ONEFOUNDRY_MAX_OUTPUT_TOKENS` (512, 1–8,192), and `ONEFOUNDRY_MAX_ELAPSED_SECONDS` (600, 30–3,600). Explicit finite context and output caps must fit within existing legacy live-text limits. Unlimited native team prompts retain provider context limits and all cancellation, operation, output and time bounds; the separate 96,000-byte legacy chat/tool-request limit remains. Unlimited workflow prompt policies save as null, never zero; historical snapshots remain intact and the UI shows the effective limit. The workflow snapshots these values; model input tokens and cost are observed provider values, not hard cost caps. An unknown attempt keeps its reservation until owner reconciliation.

Chief, direct-agent, and team chat accept operator messages beyond the former 16,000-character composer limit, up to a 1,000,000-character safety bound. The full text is saved as the operator message. For a long first Chief or direct-agent message, the work-order brief points to that saved message, which remains required in later team prompts even after normal chat history is paged out. A configured finite native context budget rejects a message that cannot fit; provider context limits still apply. Legacy Task chat keeps its separate `LIVE_TEXT_MAX_PROMPT_BYTES` limit and file-context selection rules.

In `event`, the coordinator uses `ONEFOUNDRY_COORDINATOR_POLL_SECONDS` (default 5, 1–30), `ONEFOUNDRY_COORDINATOR_LEASE_SECONDS` (60, 30–300 and greater than poll), `ONEFOUNDRY_COORDINATOR_MAX_ATTEMPTS` (3, 1–10), and `ONEFOUNDRY_COORDINATOR_ACTOR_ID` (default `onefoundry-coordinator`, distinct from the operator). It has database access only on Compose's internal network and no provider credential volume. Stop the coordinator and switch to `manual` to stop automatic order creation; saved intents remain available for review.

## Automation (event-driven coordination)

**Automation** turns events into work orders through operator rules, as designed in [docs/EVENT_DRIVEN_COORDINATION_DESIGN.md](docs/EVENT_DRIVEN_COORDINATION_DESIGN.md). Slice 1 covers internal events only: a work order becomes done, needs review, failed, unknown, or blocked; an approval is granted or rejected. `COORDINATION_MODE` defaults to `off` (nothing is recorded). `draft_only` records events and lets rules create draft work orders; `auto` also honours a rule's "Ready" choice. Nothing starts a run automatically. `COORDINATION_MAX_CHAIN_DEPTH` (1–30, default 10) limits generations of automatically created work from one event; a rule may lower it. `COORDINATION_MAX_ORDERS_PER_DAY` (1–1000, default 50) caps rule-created work per project per day, alongside each rule's own daily limit. The coordinator service matches and fulfils rules with database access only; it never calls a model. **Pause automation** stops new claims for the project; events keep queuing and resume when unpaused. Rules are versioned; every created work order records its triggering event, rule version, and chain step, and shows "Created automatically" under Task details.

**Automatic starts.** In `COORDINATION_MODE=auto` only, a rule can be set to **Start automatically**: the coordinator creates the work order as ready and queues one launch, and the in-app launcher starts one live text run for it through the normal path (assigned agent's model, prompt limits, deliverable and review rules). Launches count toward `COORDINATION_MAX_AUTO_STARTS_PER_DAY` (1–500, default 20) per project; past the cap, or if the agent cannot run, the work stays ready for the operator. A rejected run blocks the launch; an uncertain or interrupted run is unknown and never retried. Triage drafts are never started automatically. In `draft_only` mode every rule creates drafts.

**Chief task continuation.** A Chief of Staff Task chat may save several child assignments in one structured reply. Each child has its own agent, deliverable, checks, and exact creating turn; the Task chat shows their current states. In `COORDINATION_MODE=auto`, an `auto_start` child is queued for one bounded live text launch unless its deliverable is `code_change`. A code-change child becomes ready for an operator-selected coding runner, with no live-text launch queued. A confirmed child outcome queues one bounded Chief follow-up in the conversation that created the assignment, where the saved job dossier and project plan support the next decision. If that conversation was closed, the follow-up is blocked instead of posting into a newer chat. The follow-up is capped by the project coordination daily limit and stops at an unknown model outcome; it is never retried automatically. With coordination off or in `draft_only`, Chief assignments remain drafts and need an operator start. A saved assignment, successful model reply, or completed child does not by itself complete the parent. The parent still needs deliverable evidence or operator acceptance, and outbound actions still use Approvals. Coding-agent work uses its separate Execution Gateway and is not launched by this live text continuation.

**Chief-proposed agents.** Under Automation, tick the tools a proposed agent may request (the tool ceiling; empty by default). When the built-in Chief of Staff has `propose_profile_v1` in its saved and current tools, it can propose one new agent per call: name, instructions, memory scope, tools inside the ceiling, autonomy (manual or supervised), whether to reuse the Chief's model, an optional first draft work order, and a reason. The proposal appears in **Approvals** as a readable summary bound by SHA-256 to the exact proposal. Approving creates exactly that custom agent under the Chief (and its draft work order) in the same transaction as the decision; it fails with 409 if the requested tools have since left the ceiling or the name is taken. Rejecting creates nothing. Other roles cannot use the tool.

A rule can also run **on a schedule**: every day or every week at a set time in `COORDINATION_TIMEZONE` (IANA name, default `UTC`), or every 1–168 hours. The coordinator records one `schedule.fired` event per due time and nothing for times before the rule version was saved. After a pause or restart only the most recent missed time runs, and a paused project fires nothing.

**Findings and Chief of Staff triage.** A role with `report_signal_v1` in its saved and current tool list can report one finding (topic plus a 500-character summary) per call; it becomes an `agent.finding` event, never a message to another agent, and the tool is refused while automation is off. Rules can match findings by topic or agent. A finding (or, in later slices, an external event) that no rule matches goes to Chief of Staff triage: the app opens one chat per event on a standing **Automation triage** work order and makes one bounded model call with the event quoted as data. The Chief must reply with one JSON decision: create one draft for a named agent, ignore, or ask the operator. Anything else asks the operator. Triage drafts are always drafts and count toward the daily cap and chain limit. A failed call blocks the event; an interrupted or uncertain call is marked unknown and never retried. Triage runs inside the app (actor `COORDINATION_LAUNCHER_ACTOR_ID`, default `coordination-launcher`) because it needs the Chief's model credentials; the coordinator service still holds none.

**Mail inboxes (read-only IMAP).** Under Automation → Mail inboxes, connect a mailbox directly over IMAP with implicit TLS (default port 993). This works for Zoho, Fastmail, iCloud, and most hosts, including a Zoho mailbox that is also set up in Outlook: OneFoundry talks to the mail server, not to the mail app. The app password is saved only in the protected `mail` store under `MODEL_SECRET_ROOT`. **Check connection** verifies TLS, sign-in, capabilities, and the folder, and sets the starting point after the newest existing message, so no history is imported; a mailbox can be turned on only after a successful check. While automation is on, the in-app launcher checks each enabled mailbox every `MAIL_POLL_SECONDS` (15–3600, default 60), opening the folder with `EXAMINE` and fetching with `BODY.PEEK`, so nothing is marked read. Each new message becomes one `email.received` event deduplicated by server, folder, `UIDVALIDITY`, and UID; the bounded original (`MAIL_MAX_MESSAGE_BYTES`, default 256 KiB) is saved with mode 0600 and its SHA-256 under `ARTIFACT_WORKSPACE_ROOT/mail`. Rules can match by sender domain, sender address, or mailbox; unmatched mail goes to Chief of Staff triage. Email text is always quoted data and cannot change tools, autonomy, or approvals. A rejected password turns the mailbox off; a rebuilt folder (new `UIDVALIDITY`) restarts after its newest message. Nothing is sent.

**Microsoft and Google accounts.** Under Automation → Microsoft and Google accounts, add an app you registered yourself and tick the access it needs (read mail, read files, write files). Microsoft uses device-code sign-in: register a Microsoft Entra app with public client flows allowed, enter its client ID and tenant (`common` for any account), choose **Sign in**, enter the shown code at microsoft.com/devicelogin, then **Check sign-in**. Google uses a Desktop-app OAuth client (client ID and secret) and returns to `http://127.0.0.1:APP_PORT/` (override with `CONNECTOR_GOOGLE_REDIRECT_URI`, loopback only) with PKCE; publish the consent screen or use an internal Workspace app, because Testing-mode clients sign out after seven days. Scopes are the narrowest per feature (`Mail.Read`, `Files.Read.All`, `Files.ReadWrite.All`; `gmail.readonly`, `drive.readonly`, `drive.file`). Client secrets and tokens live base64-encoded in the protected `connectors` store and never reach the API, events, or models; access tokens refresh automatically and a revoked sign-in marks the account as needing sign-in. A connected account with mail access can back a **Gmail** or **Outlook.com / Microsoft 365** mailbox: the connection check records the current Gmail history ID or Graph delta link, so no history is imported, and new inbox messages are fetched as original MIME and handled like IMAP mail. A Gmail burst above `MAIL_MAX_FETCH_PER_POLL` keeps the newest messages and records the skipped count. Removing an account is refused while a mailbox uses it; Google tokens are revoked on removal.

**Watched folders.** A connected account with file access can watch one folder: a OneDrive/SharePoint path from the drive root (for example `/Contracts`) or a Google Drive folder link or ID. **Check folder** resolves it and records the provider's current change position, so existing files are not imported. While automation is on, the launcher checks each enabled folder every `DOCUMENT_POLL_SECONDS` (60–86400, default 300) and reads only files directly inside that folder. Each new file revision (up to `DOCUMENT_MAX_BYTES`, at most 4 MB, and `DOCUMENT_MAX_FILES_PER_POLL` per check) is downloaded once, saved through the project's input-file pipeline (Google Docs, Sheets, and Slides exported as DOCX, XLSX, and PPTX) so the restricted worker extracts its text, and recorded as `document.created` or `document.changed`; unsupported or oversized files are recorded with an ingest error instead. Graph download links are accepted only on Microsoft content hosts. Rules can match by folder or file type, and work they create gets the file attached, so its extracted text reaches the assigned agent. Unmatched document events are not sent to triage, to avoid a model call per file edit. Project input-file quotas still apply.

**Document writes.** A role with `propose_document_write_v1` can propose one new text, Markdown, or CSV file (up to 64 KiB, file name ending in the matching extension) for a watched folder whose account was connected with write access. The proposal appears in **Approvals** with the content and its SHA-256, bound into the approval digest. After approval, choose **Write exact file once** under Watched folders: the file is created as new (OneDrive renames on conflict; nothing is overwritten), then read back. Google Drive writes are verified by MD5 and size, OneDrive by size. A provider error marks the write failed; a lost connection or mismatched readback marks it unknown, and it is never sent again automatically. Existing-file actions are described below.

## Input files

Project creation, **Settings → Project setup**, **Work orders**, and **Task chat** accept local files. Supported extensions are `.txt`, `.md`, `.csv`, `.tsv`, `.json`, `.yaml`, `.yml`, `.xml`, `.html`, `.htm`, `.pdf`, `.docx`, `.xlsx`, `.pptx`, `.jpg`, `.jpeg`, `.png`, `.webp`, `.doc`, `.xls`, `.ppt`, `.rtf`, `.odt`, `.ods`, and `.odp`. Files are uploaded to a private project volume, processed by the restricted `input-file-worker`, and marked pending, ready as text/image, or rejected. The worker needs Poppler, Tesseract, LibreOffice, and Pillow; Compose includes them. Project and work-order text files are supplied as labeled, bounded context to live text turns; Task chat can select exact saved files for each message. Project images are sent only when explicitly selected, while images attached to a work order are part of its assigned context. A pending or rejected selected file blocks Send before provider egress. The saved turn shows the selected file IDs and exact sections or images used. A subsequent message can use the same work order and choose files again. An unknown provider outcome still requires explicit **Continue conversation**; it never resends automatically.

Image parts are currently wired for OpenAI Responses and Codex account turns, with a combined default of two images and 8 MiB. Other model providers cannot receive a selected image through this path. Large images may be saved locally but exceed the provider input limit. Office and PDF visuals embedded inside documents are extracted as text or local OCR, not forwarded as image parts. Coding-runner manifests include bounded extracted project and work-order text with source hashes; they do not stage original file bytes or visual parts. Provider image calls require a configured account and separate live acceptance.

Defaults are 25 MiB per original, 30 project files, 200 MiB per project, and eight files per work order or chat turn. Staged files count toward the project file limit. Installed operators can set the existing 1–100 project file limit with `onefoundry config set INPUT_FILE_MAX_PROJECT_COUNT 50`, then run `onefoundry restart`; the 200 MiB project byte limit still applies. `INPUT_FILE_ROOT` is a private dedicated volume. `INPUT_FILE_MAX_BYTES`, `INPUT_FILE_MAX_PROJECT_BYTES`, `INPUT_FILE_MAX_PROJECT_COUNT`, `INPUT_FILE_MAX_LINK_COUNT`, `INPUT_FILE_MAX_TEXT_BYTES`, `INPUT_FILE_MAX_VISUAL_BYTES`, and `INPUT_FILE_MAX_VISUAL_COUNT` are validated settings documented in `.env.example`. Upload calls use `POST /api/projects/{id}/input-files?scope=project|work_order|staged` with raw bytes, `X-File-Name`, and an optional client UUID in `X-Client-File-Id`; GET at the same collection and `/{file_id}` returns owner-scoped saved state.

## Start

Create `.env` with owner-only permissions. Set `DB_PASSWORD` and `APP_DB_PASSWORD` to two different long random passwords, and keep `.env` local. The migration container uses the first password to apply schema changes and provision a restricted app login. The app container receives only the second password. Run:

```sh
cd /home/ken/OneFoundry/onefoundry
umask 077
cp .env.example .env
chmod 600 .env
# Edit .env and set both passwords before starting.
docker compose up -d --build
```

If port 8025 is already used, set `MAILPIT_UI_PORT` in the local `.env` to another free loopback port before starting. OneFoundry's Mailpit receives only synthetic preview messages; its SMTP port is internal to Compose.

For real outgoing mail, open a project’s **Automation → Outgoing mail**. Add the provider’s SMTP server, TLS mode and port, username, sender address, and SMTP/app password. Check the connection, then turn sending on. Incoming IMAP credentials are separate. A running manual work order can prepare an email there; a role with `propose_email_v1` can prepare one during its run. Each exact message appears in **Approvals**, where approving makes one send attempt. The recent email list shows whether the SMTP server accepted it or whether the outcome is unknown; acceptance is not proof that the recipient received it. No account is configured by installation or update, and batch approval is not available yet. `SMTP_TIMEOUT_SECONDS` sets the 2–60 second SMTP connection bound (default 15).

Open [the readiness check](http://127.0.0.1:8765/health/ready) in a browser. A ready database and applied schema return `{"status":"ready","database":"ready"}`. `/health/live` only confirms that the HTTP process is running. To stop the local stack, run `docker compose down`; this retains the database volume.

The app is published on `127.0.0.1` only. PostgreSQL has no published port. Requests with a Host outside `localhost` and `127.0.0.1` are rejected. Writes require an Origin and Host matching the configured `APP_PORT` exactly. Compose sets database connection values, `APP_DB_USER`, `APP_ALLOWED_HOSTS`, and `APP_PUBLIC_PORT`; explicit settings override environment values. Missing or invalid passwords, ports, or allowed hosts fail validation at startup. Host settings may contain only `localhost` and `127.0.0.1`.

The API exposes `GET/POST /api/projects`, `GET /api/projects/{id}`, `GET/POST /api/projects/{id}/profiles`, and `PATCH /api/projects/{id}/profiles/{profile_id}`. List routes return bare arrays. Mutations return the saved record. The local operator actor is set by `OPERATOR_ACTOR_ID` (default `operator`); clients cannot supply it. Custom profiles accept `memory_scope` (`company` or `project`), `allowed_tools` identifier lists, and `autonomy_level` (`manual`, `supervised`, or `bounded`). `permissions_active` remains false.

Project Archive and Delete use reversible states. `GET /api/projects` lists active projects; `?status=archived` and `?status=trashed` list the other sections. `POST /api/projects/{id}/archive`, `/unarchive`, `/trash`, and `/restore` require `expected_version`; `/trash` also requires the exact `confirm_name`. Archive and Trash preserve profiles, work, artifacts, credentials, memory, and append-only events. Trash restoration returns a project to its previous active or archived state. Archived and trashed workspaces reject writes until restored; active runs, queued runner jobs, and pending approvals must be resolved before leaving Active. There is no permanent-delete endpoint.

Project-scoped `/api/projects/{id}/work-orders`, `/runs`, and `/approvals` routes record manual plans. A work order can move through `draft`, `ready`, `running`, `blocked`, `needs_review`, `done`, `failed`, and `unknown`; handoff changes the assigned profile on the same run. A completed run is assessed against the work order's declared deliverable and acceptance checks. Saved owner evidence can satisfy defined checks; otherwise the operator may accept or return it with a reason. Reopen is explicit. Each mutation and its event commit together. Run detail includes the work-order timeline, operator actor, time, configured profile model, and observed usage where available. New runs also save the original task title/instructions and append-only profile snapshots at each assignment (name, model, instructions, memory scope, tools, autonomy); search and timeline read those snapshots instead of current profile/work-order values. Runs created before this migration show unavailable historical fields rather than guessed values. An approval request stores the exact draft and its SHA-256 digest. Approve/reject records a one-shot decision. The fixed synthetic fixture merge, synthetic Sales preview, and separately approved GitHub PR comment have executable targets; other proposals remain decision records. Finish waits until pending requests are decided. Freeform proposal text and finish reason stay in owner rows, outside immutable event payloads. The restricted app login can insert events and profile snapshots but cannot update, delete, or truncate them; only the Tool Gateway code writes them.

Step 4 records one `operator_entered` result for a successfully completed manual run. The local DreamCycle creates one deterministic candidate from that result; an operator approves or rejects it once. Approval publishes a memory item with source result and candidate citations. `GET /api/projects/{id}/memory` browses recent approved items; `?query=...&limit=20` filters and scores exact word matches in PostgreSQL before limiting. Optional `scope=project` returns only project memory from that project; `scope=company` returns company memory from all projects; omitted scope returns both. Project scope is visible only in its source project. Company scope is visible from every project, while its source project ID remains attached. Results and candidates remain visible only in their source project. Rejected and pending candidates never appear in memory retrieval. Result and candidate text stays out of event payloads. Database triggers bind candidate text/scope to its result, enforce one-shot review, and require a matching approved candidate before memory publication.

The bounded candidate text normalization, deterministic proposal identity, retrieval shape, and citations were adapted from historical KJ31 memory and DreamCycle behavior. OneFoundry uses a local lexical score and has no import or runtime dependency on the frozen workers. Native embeddings remain deferred until a local embedding service is configured. Step 4 makes no embedding, AI provider, or model call. Obvious secret patterns are rejected at input; this is not a universal secret detector, so operators should keep secrets out of result summaries.

Step 5 adds an explicit `research_to_gtm` synthetic text fixture for a ready work order assigned to the built-in Researcher. `POST /api/projects/{id}/work-orders/{id}/synthetic-text-run` runs the installed OpenAI Agents SDK with two local `ScriptedModel` steps and its real Researcher→GTM handoff. It records separate cited text outputs, role actor IDs, handoff and completion events, and a `synthetic_text` run with zero tokens and cost. `GET /api/projects/{id}/runs/{id}/text-outputs` reads those outputs and exact source memory citations. Memory is selected by work-order words within the intersection of both profiles' memory scopes. Profile instructions enter the local SDK fixture; configured model IDs are recorded, but no configured provider model, web search, tool, or outbound operation is invoked. ## Repository sources

In **Settings → Repositories**, a project can save a local Git repository or a GitHub repository at an exact 40-character commit. Local discovery requires an explicitly mounted repository. For a checkout already on the computer running Docker, run this command from the `onefoundry/` directory:

```sh
python3 scripts/local_repositories.py add /absolute/path/to/repository
```

The command requires Git and Docker Compose on the host. It checks that the path is a real Git checkout root, writes an ignored owner-readable Compose override, validates it, restarts only the OneFoundry app, and confirms that Docker mounted that exact checkout read-only. It never mounts the whole home directory. Run `python3 scripts/local_repositories.py list` to see configured checkouts. Repositories with the same folder name need a distinct `--name NAME`. Each checkout is mounted once for the installation; future projects can select it in **Settings → Project setup** or **Settings → Repositories** without running the command again. Refresh the browser after adding a checkout, select the discovered name, and confirm the saved branch and revision.

The private override is generated from `compose.local-source.example.json`; its `LOCAL_SOURCE_ROOT`, `git_timeout_seconds`, and `compose_timeout_seconds` values are validated by the command. If you later rebuild the app, include the override: `docker compose -f compose.yaml -f compose.local-source.json up -d --build`. Discovery checks the root and up to 25 immediate entries within 10 seconds; each Git subprocess in the app is limited to 3 seconds. The browser shows branch, HEAD, and dirty status. Selection rechecks the path and HEAD. This mount gives the app read access for metadata only. The trusted local coding worker currently accepts only the built-in disposable calculator fixture; selecting a repository does not make it a coding target. An absolute host path typed into the browser is not a repository selection.

Prebuilt installations retain approved source access through `data/config/local-sources.compose.json` under the installation home. Configure the existing `LOCAL_SOURCE_ROOT` in the private installed `.env`; its value is a dedicated absolute container directory. The optional JSON file must be owned by the operator, mode `0600`, and contain only `{"services":{"app":{"volumes":[{"type":"bind","source":"/absolute/approved/checkout","target":"/configured/root/repository-name","read_only":true}]}}}`. Each source must be a real checkout directory with its own `.git` directory; each target is one named repository under the configured root. Writable mounts, other services, extra Compose fields, symlinks, duplicate mounts and environment substitutions are rejected. Ambient shell variables cannot replace installed configuration. Commands using updater 0.10.10 or later retain these mounts across start, restart, update and rollback; older updaters do not know this overlay. The default `LOCAL_SOURCE_ROOT` is `/source-roots/workspace`, a dedicated container directory with no automatic host bind. After mounting, select the current committed revision and explicitly grant `repository_file_v1` to the required profiles. Native team source reads use `TEAM_REPOSITORY_READ_ENABLED=true` by default; set it to `false` in the private installed `.env` to disable them. Explicitly empty `LOCAL_SOURCE_ROOT` is invalid while enabled. Bounded safe committed text from mounted, selected sources may enter configured team model providers. Profile allowlists and project/source/revision/path/secret checks still apply at each read. This gate applies only to native team sessions; legacy live-text source/diff exclusions remain intact, and other excluded tools gain no access. Reads reject revision drift and protected files; uncommitted working changes are not architecture evidence.

GitHub accounts are entered in **Settings → Repositories** with a token. Tokens live in a protected `github` subdirectory of `MODEL_SECRET_ROOT`; the API returns only credential presence. Repository discovery contacts only `https://api.github.com`, follows no redirects, and shows up to the first 50 accessible repositories. A repository outside that page can be entered by owner and name. Selection verifies the repository and branch through GitHub and saves the branch head SHA. Saved sources can be removed; a GitHub account can be disconnected after its saved sources are removed. No clone, branch write, PR, or merge is performed by this connection.

Runner settings are `RUNNER_SPOOL_ROOT` (absolute dedicated directory, default `/runner-spool`), `RUNNER_WALL_SECONDS` (1–60, default 30), `RUNNER_MAX_LOG_BYTES` and `RUNNER_MAX_DIFF_BYTES` (512–65536, defaults 65536 and 32768), and `RUNNER_RECEIPT_WAIT_SECONDS` (at least wall seconds plus 30, at most 600, default 120). The configured limits enter each immutable manifest. Compose fixes the spool path at `/runner-spool` for both app and runner and reads the other settings from `.env`; explicit application settings override environment values for direct installations with a matching runner path. Live provider usage is recorded when reported; actual provider billing may differ.

Step 7 lets a completed synthetic Researcher → GTM run create a local Sales draft. An exact inbox approval permits one SMTP submission to OneFoundry's Mailpit, followed by readback of the recipient, subject, and normalized body hash. A rejection submits nothing. A missing or mismatched readback leaves the delivery `unknown` and is never automatically retried. A confirmed delivery or a verified passing QA receipt can be staged as a DreamCycle candidate; an operator must still approve it before it is searchable memory. Rejected or unknown Sales drafts cannot become candidates.

Infra is a read-only view of this Compose stack. From this folder, run the host observer in a separate terminal:

```sh
python3 scripts/infra_snapshot.py --compose-file compose.yaml --output .infra-status/status.json --service app --service db --service runner --service mailpit --watch --interval-seconds 5
```

The observer writes a small status snapshot into the ignored `.infra-status` directory; the app only reads that directory through a read-only bind mount. `INFRA_SNAPSHOT_PATH` and `INFRA_SNAPSHOT_MAX_AGE_SECONDS` are validated settings. If the observer stops or its snapshot becomes stale, Infra reports `unknown` rather than assuming the stack is healthy. The app has no Docker socket or cloud access.

### Coordination audit follow-up

Rules expose **Most automatic model attempts per day** and optional quiet hours in project time. This is a cap on admitted automatic starts originating from a rule, across its versions; failed and unknown starts count. It does not count every child model turn or tool request. Quiet hours defer automatic starts without waking an agent or consuming an admission. Rule creation limits and team-turn limits remain separate.

Mail replies carrying a saved outbound Message-ID in `In-Reply-To` or `References` inherit that sending work order's chain depth, including an uncertain submission. Unsent proposals and another project's mail do not establish lineage. `MAIL_IDLE_ENABLED=true` uses bounded read-only IMAP notification waits (`MAIL_IDLE_WAIT_SECONDS`, 5–120, default 60) alongside normal polling. A notification makes the mailbox due for its existing ingestion path; IDLE never starts a model or reads messages itself. Polling remains the fallback. Paused projects and disabled mailboxes have no IDLE waits.

Work orders and run timelines show **Triggered by**, including the event and originating rule version or triage. Manual work has no invented trigger.

**Settings → Accounts & files** offers folder-name search and exact Excel/Google Sheets range reads. Search visits only direct files in the selected folder, with `DOCUMENT_SEARCH_MAX_PAGES` (1–20, default 5) and `DOCUMENT_SEARCH_MAX_RESULTS` (1–100, default 20); the UI reports a truncated search. `DOCUMENT_MAX_RANGE_CELLS` (1–10000, default 1000) bounds literal rectangles such as `A1:B2`; whole columns and named ranges are rejected. Role capabilities are `document_search_v1`, `document_range_v1`, and `propose_document_action_v1`. These use the existing live-text role-tool path; team sessions currently expose their own coordination tools and do not yet bridge general role tools.

**Existing file changes** supports uploading a new version from an attached project/work-order file, exact literal cell edits, and sharing with one email recipient as reader or editor. The approval inbox shows the replacement identity, before/after cells, or recipient and access. File replacement preserves its file ID and type; native Google Docs/Slides need a dedicated edit adapter, while native Sheets use range edits. Sharing retains existing access and sends no notification email; public links and domain-wide grants are unsupported. Formula-like cell text is rejected and Sheets use RAW input. ## Self-extension design

[Self-extension plan](docs/SELF_EXTENSION_DESIGN.md) describes verified capability inspection, linked Engineer/Codex work, independent QA, approval-bound activation and resumption of the original request. The scoped native path is implemented, with installed evidence in the [0.18.3 acceptance record](docs/SELF_EXTENSION_COMPLETION.md). [Capability readiness](docs/CAPABILITY_READINESS.md) describes the inspection owner; the [runtime guide](docs/SELF_EXTENSION_RUNTIME.md) covers current setup and operation. Flags alone do not make an arbitrary repository a coding target.

The isolated coding broker validates bounded SSE event records, including the optional stream end marker. Only one proved completed response is admitted. Transport diagnostics preserve safe error categories without provider bodies or credential content; an interrupted attempt remains unknown and is never replayed automatically. A sole explicit provider-overload rejection may retry once before delivering any response to the child, within the existing request/time limits; the private worker JSON owns this bounded exception.

Known maintenance dispatch rejections now stop that saved launch intent and return a blocked assignment to Chief. Manifest-size failures are identified before provider launch; Chief can cancel or replace the inactive branch through its existing workflow. A durable coding attempt or an active model turn prevents this prelaunch recovery from changing execution state. Configured patch and transport bounds still apply.

Maintenance source-safety observations use the existing `repository_code_policy.max_context_file_bytes` / approved target `max_context_file_bytes` for each complete before/after file, and `max_tree_bytes` for the combined observation. The separate patch and ordinary command-output limits still apply. Source bytes, including leading and trailing whitespace, are preserved before protected-content validation.
